# Деньги: мерчанты и платёжный flow

Контур B. Код: `apps/core/src/payments/*`, `packages/payments/*`. Таблицы: `payment_merchant`, `plan`, `payment`, `ledger_entry`, `subscription_activation`, `referral_reward`.

## Мерчанты живут в БД, а не в env

`payment_merchant` — подключённый платёжный аккаунт. Это отличие от прода gavy-vpn, где ключи лежали в env и любая правка требовала рестарта.

| Колонка | Смысл |
|---|---|
| `provider` | `stars` \| `cryptobot` \| `oxapay` \| `paritypay` \| `pal24` |
| `alias` | человекочитаемое имя; unique `(org_id, alias)` |
| `is_enabled` | включение/выключение без деплоя (по умолчанию `false`) |
| `mode` | `live` \| `test` |
| `priority` | порядок в UI и при переборе |
| `credentials` | ключи провайдера, **зашифрованы** |
| `settings` | некритичное: TTL счёта, активы, метод (`sbp`/`card`), опциональный `api_url` |
| `purposes` | какие назначения разрешены этому аккаунту |
| `last_check_at` / `last_check_ok` / `last_check_error` | результат кнопки «Проверить» |

Что это даёт: несколько аккаунтов одного провайдера (A/B, разные юрлица, failover при блокировке), переключение без рестарта, test/live.

### Шифрование кредов

`credentials` шифруются AES-256-GCM (`@vpn/core-kit/crypto`) ключом `SECRETS_MASTER_KEY` из env. Формат значения — `v1.<iv>.<tag>.<ciphertext>` в base64; ключ шифрования = `sha256(masterKey)`.

- Шифрование при записи, расшифровка — только в момент вызова провайдера (`MerchantService.toConfig`).
- Наружу креды не отдаются никогда: `listForAdmin` прогоняет их через `maskCredentialsForDisplay`, админка видит только факт наличия.
- `core` **не стартует** без `SECRETS_MASTER_KEY` и при длине ключа < 16 символов. Дефолта тут быть не может: со значением из публичного репозитория дамп БД расшифровывается кем угодно.
- Смена ключа делает уже сохранённые креды нечитаемыми — ротация означает переввод ключей мерчантов.
- Модель угроз честная: ключ и шифртекст на одном боксе. Это защита от дампа БД / бэкапа / попадания в лог, **не** от компрометации хоста.

### Базовые URL провайдеров — константы, не настройка

`packages/payments/src/provider-urls.ts`:

| Провайдер | Base URL | Разрешённые хосты |
|---|---|---|
| `stars` | — (внешнего API нет) | — |
| `paritypay` | `https://api.paritypay.ru` | `api.paritypay.ru` |
| `pal24` | `https://pal24.pro/api/v1` | `pal24.pro` |
| `cryptobot` | `https://pay.crypt.bot/api` | `pay.crypt.bot`, `testnet-pay.crypt.bot` |
| `oxapay` | `https://api.oxapay.com/v1` | `api.oxapay.com` |

Раньше адаптеры брали хост из `settings.api_url`, который приезжал PATCH-ом из админки: подменённый адрес уводил расшифрованный боевой токен на чужой сервер. Теперь `api_url` принимается, только если он https, без user/password в URL и его хост есть в allowlist; иначе настройка молча отбрасывается с warning-ом, а адаптер берёт константу. Единственная легальная причина переопределения — testnet CryptoBot.

## Пять провайдеров, один контракт

`PaymentAdapter` (`packages/payments/src/types.ts`): `isConfigured`, `createInvoice`, `verifyWebhook`, `parseWebhook`, опциональный `healthCheck`. В проде интерфейс был заточен под Stars и его реализовывал ровно один класс — остальные четыре жили мимо.

| Провайдер | Назначения | Подпись вебхука |
|---|---|---|
| `stars` | topup, plan, gift | внешнего вебхука нет; подлинность даёт Telegram |
| `cryptobot` | topup, plan, gift | HMAC-SHA256 по сырому телу, ключ = `sha256(apiToken)` |
| `oxapay` | **только topup** | HMAC-SHA512 по сырому телу, ключ = merchant API key |
| `paritypay` | topup, plan, gift | HMAC-SHA256 по конкатенации полей |
| `pal24` | topup, plan, gift | `strtoupper(md5("OutSum:InvId:token"))` |

Алгоритмы перенесены буквально из прода и покрыты тестами (`packages/payments/src/payments.test.ts`, 22 теста). Подпись считается по **сырым байтам** тела: ре-сериализованный JSON меняет байты и ломает проверку, поэтому core поднимается с `rawBody: true`.

`supportedPurposes` — не декорация: `createPayment` отказывает, если провайдер не умеет назначение (oxapay в проде умел только topup, и это регулярно всплывало).

## Платёжный flow

Единый на всех провайдеров — вместо пяти почти одинаковых flow-сервисов (~2500 строк copy-paste), из-за которых статусы разошлись: у одного провайдера expired-платёж дозачислялся, у другого терялся вместе с деньгами. Ветвление осталось только внутри адаптера.

### Создание счёта

1. `POST /internal/payments/create` (заголовки: `x-service-token`, `x-client-request-id`).
2. Идемпотентность по `x-client-request-id` — `IdempotencyService`. Хранилище — **память процесса**, TTL 24 ч; при горизонтальном масштабировании сюда подставляется Redis. Последний рубеж в любом случае — unique-индексы БД.
3. Проверка: провайдер поддерживает назначение, ключи на месте.
4. Сумма: `topup` — из тела запроса, `plan`/`gift` — из активного тарифа.
5. Строка `payment` со статусом `pending` создаётся **до** обращения к провайдеру: если провайдер ответит, а мы упадём, вебхук всё равно найдёт запись по `order_id`.
6. Вызов `createInvoice`, обновление строки (`provider_payment_id`, `provider_ref`, `expires_at`, крипто-поля, `rate_locked_at`, сырой ответ в `meta` с маскированием).
7. Ошибка провайдера → статус `failed`, исключение наверх.

`callback_url` собирается как `PUBLIC_API_URL + /webhooks/<provider>` — то есть значение env напрямую определяет, куда провайдер пришлёт подтверждение.

### Приём вебхука

`POST /webhooks/:provider`, порядок жёсткий:

1. **Подпись.** Мерчанты того же провайдера перебираются, пока чья-то подпись не сойдётся, — так вебхук находит свой аккаунт при нескольких подключённых. Не сошлось ни у кого → **401** до всякой обработки.
2. **Поиск платежа** по `(org, provider, provider_payment_id)`.
3. **Не-`paid` статус** — просто переносится в строку (только из `pending`) и выход.
4. **Сверка суммы.** Подписи достаточно для подлинности отправителя, но не для того, что оплачено именно столько, сколько выставлено: без этой проверки корректно подписанный вебхук на 10 ₽ закрывал бы тариф за 500 ₽. Недоплата → статус `processing`, пометка `meta.amountMismatch`, **не фулфилим** (ручной разбор). Переплата принимается: деньги пришли, отказать в доступе хуже, излишек виден в `meta`. Допуск — 1 копейка на округления курса. Провайдер, не присылающий сумму, проверку проходит.
5. **Атомарный claim статуса**: `UPDATE … SET status='paid' WHERE id=? AND status IN ('pending','processing','expired','failed') RETURNING *`. Ноль строк = повторная доставка, выходим с `alreadyProcessed`.
   - `expired` в списке: платёж мог истечь по нашему TTL, а деньги реально пришли.
   - `failed`: мы сами ставим `failed` при ошибке создания счёта и по FAIL-вебхуку; если провайдер потом подтвердит оплату, не зачислить её — значит забрать деньги без услуги.
6. **Фулфилмент в той же транзакции** (см. ниже).
7. **Атрибуция — после коммита**, отдельным подключением: внутри чужой транзакции она не увидела бы незакоммиченный платёж. Её падение только логируется — деньги важнее статистики.

Ответ провайдеру — **200 даже при внутренней ошибке**, иначе он завалит ретраями. Обратная сторона: тихий сбой обработки означает «деньги у мерчанта, услуги нет, никто не знает» — это закрывает джоба `payment-reconcile` (`workers.md`).

Под то же 200 попадает и случай «нет ни одного включённого мерчанта этого провайдера»: исключение ловится общим `catch` контроллера. То есть выключенный в админке мерчант, которому продолжают приходить вебхуки, снаружи выглядит как успешно принятый платёж. В логе это видно, у провайдера — нет.

### Фулфилмент (ledger-first)

`LedgerService.fulfillPayment` в одной транзакции:

1. `ledger_entry` `+amount` типа `topup`, ключ `topup:<paymentId>`.
2. Для `purpose=plan`: `ledger_entry` `−price` типа `purchase` (ключ `purchase:<paymentId>`), запись в `subscription_activation` (unique по `payment_id` — второй вебхук лишних дней не даст), продление `expire_at` (от текущей даты окончания, если она в будущем, иначе от сегодня), обновление лимитов тарифа и **синхронизация squad'ов**.
3. Пометка первой оплаты подписчика (`is_first_paid`) условным UPDATE-ом.

Про squad'ы отдельно: без синхронизации оплата не давала доступа вообще — подписка «активна», конфиг отдаётся, но `vless_uuid` не попадал в desired-state ноды, и Xray рвал хендшейк. Лишние squad'ы снимаются, чтобы при смене тарифа доступ не накапливался.

Про `is_first_paid`: пометить и поймать конфликт нельзя — в Postgres нарушение partial unique обрывает **всю** транзакцию, и JS-catch внутри неё бесполезен. Условие проверяется внутри самого UPDATE, конфликт не возникает.

Баланс нигде не хранится: `getBalance` = `SUM(ledger_entry.amount_kopeks)`.

### Telegram Stars — отдельный путь

У Stars внешнего вебхука нет: `POST /webhooks/stars` отвечает 404 (публичная точка без подписи означала бы «зачисли себе любую сумму бесплатно»). Апдейты приходят боту, он зовёт:

- `POST /internal/payments/stars/pre-checkout` — сверка payload и суммы в звёздах до списания;
- `POST /internal/payments/stars/confirm` — подтверждение, дальше тот же атомарный claim + ledger, что и у остальных.

Курс «копеек за звезду» — настройка мерчанта `stars_to_kopeks_rate` (дефолт 100), одинаковый в адаптере и в контроллере: иначе счёт выставлялся бы по одному курсу, а сверялся по другому.

Заголовок-маркер внутреннего подтверждения вырезается из входящих заголовков публичного вебхука — снаружи он прийти не может.

## Админский API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/admin/merchants` | список с масками кредов и флагом `isConfigured` |
| GET | `/api/admin/merchants/provider-specs` | описание полей формы подключения |
| POST | `/api/admin/merchants` | подключить аккаунт |
| PATCH | `/api/admin/merchants/:id` | правка; в `credentials` передаются только изменяемые ключи, пустая строка = удалить ключ |
| POST | `/api/admin/merchants/:id/check` | health-check, результат пишется в строку |
| GET | `/v1/payments/provider-specs` | те же спеки, публично (админка ходит и сюда) |

Форма подключения рисуется по `PROVIDER_SPECS`, а не по хардкоду в UI. Базового URL в спеке нет намеренно — это константа кода.

`healthCheck` у провайдера без своей проверки возвращает «ключи на месте», у ненастроенного — «не заданы ключи»; результат в любом случае сохраняется в `last_check_*`.

## Проверено вживую

Поддельная подпись → 401; валидная → подписка +30 дней и ledger ±500 ₽; 8 повторных доставок (3 последовательных + 5 параллельных) не задвоили ни дни, ни деньги.
