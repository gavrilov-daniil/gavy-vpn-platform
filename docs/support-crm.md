# Контуры C и D: поддержка, CRM, рассылки

Код: `apps/core/src/support/*`, `apps/core/src/crm/*`, `apps/core/src/broadcast/*`. Всё, что клиент видит, идёт через бота (`apps/bot/README.md`); core сам в Telegram не ходит — он зовёт бота по `BOT_INTERNAL_URL` с заголовком `x-service-token`.

## Контур C — поддержка

Модель: `support_contact` → `conversation` → `message`.

### Входящее сообщение

`POST /internal/support/inbound` (из бота). Три барьера идемпотентности, все на индексах БД:

| Индекс | Что защищает |
|---|---|
| `support_contact_uq (org_id, telegram_user_id)` | один контакт на пользователя Telegram |
| `conversation_open_uq (contact_id) WHERE status IN (open,pending)` | один незакрытый диалог у контакта |
| `message_tg_update_uq (telegram_update_id)` | повторная доставка апдейта не задваивает сообщение |

Порядок важен: дедуп апдейта проверяется **до** работы с диалогом. Иначе повторная доставка на уже закрытом диалоге открывала бы новый — пустой, без единого сообщения.

Гонка двух параллельных апдейтов ловится не блокировкой, а конфликтом вставки: проигравший возвращает `deduped: true` с тем же `conversationId`.

### Ответ оператора

`POST /api/admin/support/conversations/:id/reply`:

1. Сообщение пишется в БД со статусом `pending` и `dedup_key`.
2. `BotClient.notify` доставляет его в Telegram.
3. Результат фиксируется: `markDelivered` (+`telegram_message_id`) или `markFailed` (+текст ошибки).

`dedup_key` детерминирован в пределах минуты (`op:<conversationId>:<sha256(text|minute)[0..16]>`): двойной клик «Отправить» с тем же текстом не задваивает сообщение, а осознанный повтор позже — уже новое.

### Статусы и назначение

`open` → `pending` → `resolved` / `closed`. `PATCH /api/admin/support/conversations/:id` меняет статус и/или `assigneeUserId`. Попытка переоткрыть диалог, когда у контакта уже есть незакрытый, отдаёт 409 — это нарушение `conversation_open_uq`, обработанное как штатная ветка.

### AI-подсказки операторам

Код: `apps/core/src/ai/*`. **ИИ никогда не пишет клиенту.** Он создаёт черновик, который оператор принимает, правит или отклоняет; наружу текст уходит существующим путём ответа оператора.

#### Провайдер подключается из админки, а не из env

`ai_provider` повторяет модель `payment_merchant`: ключ шифруется AES-256-GCM (`SECRETS_MASTER_KEY`), тумблер включает провайдера без рестарта, наружу ключ отдаётся маскированным. Ключей в env нет осознанно — иначе смена ключа означала бы выкатку.

Адаптеров два, и это не симметрия ради симметрии: у них разные адреса, заголовки и форма ответа.

| Провайдер | Модель по умолчанию | Адрес |
|---|---|---|
| `anthropic` | `claude-sonnet-5` | `api.anthropic.com` (переопределение только на loopback) |
| `openai_compatible` | `gpt-4o-mini` | любой **https**-хост или loopback — смысл адаптера в том, чтобы ходить через прокси |

Урок мерчантов повторён: адрес API приходит из тела PATCH-а, и адаптер пойдёт по нему с расшифрованным ключом. Поэтому `http` допускается только на loopback (свой vllm/ollama на этой же машине), а логин с паролем в URL отбрасываются — они уезжают в `Authorization` чужого прокси.

Вызов идёт через `request()` из `@corelink/core-kit`: таймаут, один retry, аудит в `external_api_log` с маскированием. Второго HTTP-слоя нет.

У Anthropic в теле явно стоит `thinking: {type: "disabled"}`: на новых моделях размышления включены по умолчанию, а `max_tokens` ограничивает их **вместе** с текстом — короткая подсказка обрывалась бы на середине. Ответ с `stop_reason: "refusal"` приходит с HTTP 200 и пустым `content`, поэтому проверяется до чтения текста.

#### База знаний

`kb_document`, поиск — обычный FTS Postgres по индексу `kb_document_fts_idx` (`to_tsvector('russian', title || ' ' || body)`). Ни pgvector, ни эмбеддингов: база поддержки — десятки документов, а расширение плюс модель эмбеддингов означают внешнюю зависимость в горячем пути ради того, что решается одним GIN-индексом.

`plainto_tsquery` склеивает слова через **AND**, и вопрос «как оформить возврат средств» не находил документ про возврат из-за одного лишнего слова. Операторы меняются на OR уже в разобранном запросе (`replace(plainto_tsquery(...)::text,'&','|')::tsquery`), порядок задаёт `ts_rank`. Стемминг и стоп-слова остаются за Postgres.

Удаления документов нет: выключённый (`is_active = false`) не участвует в поиске, но остаётся читаемым по ссылкам `retrieved_doc_ids` уже выданных подсказок.

#### Флоу подсказки

1. Пришло сообщение клиента → `handleInbound` ставит джобу `ai-suggest` (`QueueService.enqueue`). Генерация **не** в HTTP-хендлере приёма: клиент не ждёт модель, а упавший провайдер не мешает принять обращение. Cron `2-57/5` — страховка на случай, когда постановка не доехала.
2. Джоба генерирует подсказку в статусе `proposed`.
3. Оператор в админке видит её рядом с перепиской: текст, модель и названия документов, на которых она основана.
4. «Принять» → `accepted`, «Править» → при отправке `edited`, «Отклонить» → `rejected`.
5. Отправка — обычный `POST /api/admin/support/conversations/:id/reply`, в теле добавляется `suggestionId`. Статус `sent` ставится **после подтверждённой доставки**: иначе «отправлено» стояло бы у текста, которого клиент не видел.

`content` подсказки всегда хранит исходный ответ модели — даже когда оператор его переписал. Иначе сравнивать качество подсказок будет не с чем; факт правки виден по статусу `edited`.

**Идемпотентность — два барьера, оба на индексах:**

| Барьер | Что защищает |
|---|---|
| `job_dedup(key)` = `ai_suggest:ai:<conversationId>:<messageId>` | claim **до** вызова модели: параллельный воркер не платит второй раз |
| `ai_suggestion_idempotency_uq (idempotency_key)` | гонка двух вставок на одно сообщение |

Ключ детерминирован: `ai:<conversationId>:<messageId>`. Кнопка «Сгенерировать» снимает только claim — если подсказка уже есть, вернётся она же, второй строки не появится.

**Claim не снимается при ошибке провайдера.** Это осознанно: снятый claim означал бы повтор на каждом тике cron'а, то есть долбёж лежащего провайдера и трата денег. Оператор при необходимости жмёт «Сгенерировать» сам.

#### Что не уходит в модель

В промпт идёт переписка клиента — персональные данные, и утечка отсюда необратима. Вырезается двумя слоями (`redactSecrets`, тест `suggestion.prompt.test.ts`):

- точные секреты этого клиента из БД (`vless_uuid`, `short_uuid`, ссылка подписки) — шаблон не знает, что «a1b2…» это чей-то `short_uuid`;
- общие шаблоны — `vless://`/`ss://`/`trojan://`-ссылки целиком, любой URL с длинным токеном, uuid, длинный hex, base64-ключи (pbk), значения полей `token`/`secret`/`password`/`api_key`/`sid`/`pbk`.

Обычный текст и ссылки без токенов не трогаются: `https://youtube.com` в жалобе клиента должен дойти до модели.

#### Потолки расхода

Лимиты живут в `settings` провайдера и правятся из админки, а не деплоем:

| Настройка | По умолчанию | Зачем |
|---|---|---|
| `max_context_chars` | 12000 | сколько переписки и документов уходит в промпт (документам — не больше 60%, иначе длинная статья вытеснит сам вопрос) |
| `max_output_tokens` | 700 | потолок ответа |
| `max_per_conversation` | 20 | зациклившийся диалог не доит модель |
| `max_per_day` | 300 | последний рубеж по деньгам на организацию |

Провайдер не подключён, выключен, лежит или лимит исчерпан → подсказки просто нет. Приём обращения, переписка и ответ оператора работают как раньше.

## Контур D — CRM

### Атрибуция по deep-link

Ссылка вида `t.me/<bot>?start=c_<CODE>`. Код — 6 символов из алфавита без `0/O/1/I` (его набирают руками с рекламы), генерится случайно, коллизию ловит `campaign_link_code_uq`, а не проверка перед вставкой.

Невалидный или неизвестный код — **не ошибка**: пользователь просто считается органикой.

**First-touch.** `subscriber.campaign_link_id` пишется условным `UPDATE … WHERE campaign_link_id IS NULL`. Приход по другой ссылке позже даёт событие с `meta.revisit` и не крутит счётчик. Именно поэтому при создании подписчика колонка не заполняется сразу: заполнил бы — claim не сработал бы, и регистрация засчиталась бы как повторный приход.

Счётчик `registrations` растёт только при одновременном выполнении: событие вставилось (partial unique `campaign_event_registration_uq`) **и** это был first-touch.

**Атрибуция платежа.** `payment.campaign_link_id` проставляет триггер `trg_payment_set_campaign_link` при вставке — снимок источника делается в БД, а не дублируется в каждом месте создания платежа (в проде это дублировалось в пяти flow-сервисах). `AttributionService.onPaymentPaid` только читает снимок и разносит по счётчикам, барьер — `campaign_event_payment_uq (payment_id)`.

Уникальные плательщики считаются по флагу `payment.is_first_paid`, который стоит под partial unique `payment_first_paid_uq`. Подсчёт прошлых событий этого не давал: два параллельных первых платежа оба видели «прошлых нет» и давали +2.

### Воронка

`GET /api/admin/funnel?days=30`. Этапы из `bot_event`: `start` → `plans_open` → `plan_selected` → `pay_method_open`; далее из таблицы `payment`: `payment_created` → `payment_paid`. Плюс разбивка по дням (новые подписчики, платежи, выручка) и коэффициент `startToPaid`.

`POST /internal/bot-events/track` дедуплицируется по `bot_event_update_uq (update_id)`: повторная доставка вебхука Telegram не раздувает воронку.

Статистика кампании (`GET /api/admin/campaigns/:id/stats`) считается по `campaign_event` — источнику истины; денормализованные счётчики в `campaign_link` существуют только для быстрого UI. Отдаётся ещё `costKopeks`, `profitKopeks`, конверсия и CPA.

## Рассылки и касания

### Одна отправка — `DispatchService`

Барьер: строка в `message_log` пишется **до** отправки и служит claim'ом. Конфликт по `dedup_key` = адресат уже взят другим воркером или прошлым запуском.

| Исход | Что делает |
|---|---|
| `sent` | сохраняет `telegram_message_id` |
| `duplicate` | claim не взят, выходим |
| `blocked` (403) | ставит `subscriber.tg_blocked = true`, строка остаётся как след — повторять бессмысленно |
| `rate_limited` (429) | до 3 повторов с паузой `retryAfter` (не более 60 с) |
| `error` | **claim снимается** — иначе `dedup_key` навсегда закрывает повтор этому адресату (рестарт бота на минуту = сотни человек без рассылки) |

### Рассылки

Получатели материализуются в `broadcast_recipient` сразу при создании: рассылка становится возобновляемой (упал воркер — второй запуск доберёт `pending`) и её размер известен до старта. Unique `(broadcast_id, subscriber_id)`.

Прогон из админки идёт **фоном в процессе** (`void this.broadcasts.run(id)`), ответ — `{started:true}`: держать HTTP-соединение на всё время рассылки нельзя. Прогресс — через `GET /api/admin/broadcasts/:id`. Добор упавших прогонов — джоба `broadcast-resume` (`workers.md`).

Темп — `throttle_per_sec` (по умолчанию 20), пауза считается как `1000/throttle`.

Сегменты (`SEGMENT_KINDS`): `all`, `active`, `inactive`, `expiring` (горизонт в днях), `segment` (сохранённый предикат).

Предикат сегмента — **узкий декларативный набор полей**, а не произвольный SQL: `status`, `expiresInDays`, `expiredWithinDays`, `createdWithinDays`, `languageCode`, `campaignLinkId`, `hasPaid`. Произвольное правило из админки — это дыра в БД.

Маркетинговая выборка (по умолчанию) исключает `marketing_opt_out` и `tg_blocked`.

### Триггерные касания

`touchpoint` с `trigger_key` из трёх: `trial_no_payment`, `expires_soon`, `expired_recently`. Запуск — джоба `touchpoints-run` раз в час, плюс ручной `POST /api/admin/touchpoints/run`.

Окно попадания — 24 часа от `delay_hours`. Без окна условие «триал старше N часов» держалось бы вечно и цель попадала бы в выборку бесконечно.

**Дедуп по «якорю» триггера, а не по календарной дате.** Ключ — `touchpoint:<id>:<subscriberId>:<anchor>`, где anchor = epoch от `trial_used_at` или `expire_at`. С датой окно в 24 ч, пересекающее полночь UTC, попадало в выборку в двух разных днях и давало два сообщения одному человеку. С якорем:

- `trial_no_payment` — ровно один раз (`trial_used_at` ставится однажды);
- `expires_soon` / `expired_recently` — один раз на каждый `expire_at`, то есть касание штатно повторяется после продления и не повторяется внутри одного срока.

Тихие часы (`quiet_hours`, UTC, интервал может пересекать полночь) пропускают весь прогон касания.

Транзакционные уведомления (`subscription-notify-expire`) `marketing_opt_out` **не учитывают** осознанно: это уведомление о доступе, а не маркетинг. `tg_blocked` учитывается — в заблокировавшего бота слать бессмысленно.

## Админка

`apps/admin` — React 18 + Vite 6, статический SPA, 11 экранов (порядок — как в `App.tsx`). Колонка «Роль» — минимальная роль, которой экран виден; список в меню собирается по ней, а закрывает раздел гвард в core (`security.md`):

| Экран | Роль | Что делает |
|---|---|---|
| Поддержка | support | диалоги, переписка, ответ оператора, статус и назначение; вкладка «База знаний» (саппорту на чтение), вкладка «Провайдер ИИ» — только admin |
| Подписчики | support | список подписок: статус, срок, трафик, баланс, устройства. Отвязка устройства и перевыпуск ссылки — от admin |
| Мерчанты | superadmin | подключение провайдеров, ключи (маскированные), test/live, приоритет, health-check |
| Инфраструктура | admin | серверы, config-профили, inbound'ы, host'ы, squad'ы: полный CRUD над сетевой моделью |
| Ноды и каскады | admin | список нод со сходимостью, rebuild, desired-state, создание каскадов, привязка каналов |
| Трафик | admin | расход по подписчикам, по дням, по странам и нодам, разрез по платформам |
| Продажи | admin | воронка, динамика по дням, кампании и ссылки, ROI |
| Рассылки | admin | создание, фоновый прогон, повтор упавших, триггерные касания |
| Тарифы | admin | создание, правка, включение и выключение — через админские `/api/admin/plans` |
| Доступ | admin | операторы и роли, заявки из Telegram, пароли, настройка входа по Telegram |
| Мой профиль | support | своя учётка: привязка Telegram и смена пароля |

Про тарифы: экран ходит в `GET/POST /api/admin/plans` и `PATCH /api/admin/plans/:id`, а не в публичный `/v1/plans`. Разница существенная: публичный эндпоинт отдаёт только включённые тарифы, и на нём выключенный тариф нечем было бы включить обратно. Флаг `is_active` при создании не передаётся (эндпоинт его не принимает) — новый тариф всегда рождается включённым, выключается вторым действием.

**Вход.** `AuthGate` показывает форму email+пароль и, если вход по Telegram включён, кнопку Login Widget; полученный токен сессии кладётся в `localStorage` и уходит в заголовке `x-admin-token`. Отдельным сворачиваемым блоком остаётся ввод переходного общего `ADMIN_TOKEN` — им заводится первая учётка, дальше он не нужен. Роль оператора приходит из `GET /api/admin/auth/me` и лежит в контексте (`session.ts`, `useCan`).

Dev-сервер на `:3200` проксирует `/api` и `/v1` на `http://localhost:3100`. Отдельный путь `/v1` нужен потому, что тарифы и спеки провайдеров отдаются публичным API core, а не под `/api`.
